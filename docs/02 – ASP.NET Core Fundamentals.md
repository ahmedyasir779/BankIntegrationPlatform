# 02 – ASP.NET Core Fundamentals

---

# Overview

Before understanding controllers, middleware, dependency injection, or Clean Architecture, it is essential to understand what **ASP.NET Core** actually is.

Many developers learn how to build APIs by copying code without understanding what happens behind the scenes. This chapter focuses on the internal architecture of ASP.NET Core and explains how our application is hosted, how requests are processed, and why the framework is designed the way it is.

Understanding these fundamentals will make every future concept in this project significantly easier to understand.

---

# What is ASP.NET Core?

ASP.NET Core is Microsoft's modern, cross-platform framework for building:

* REST APIs
* Web Applications
* Microservices
* Real-time applications
* Cloud-native applications
* Minimal APIs
* gRPC services

Unlike older versions of ASP.NET that only ran on Windows and IIS, ASP.NET Core runs on:

* Windows
* Linux
* macOS
* Docker
* Kubernetes
* Azure
* AWS
* Google Cloud

This portability is one of the reasons ASP.NET Core has become the standard framework for modern backend development with .NET.

---

# What is .NET?

ASP.NET Core is **not** the .NET runtime itself.

Think of the relationship like this:

```text
.NET
│
├── Runtime
├── Base Class Library (BCL)
├── Garbage Collector
├── JIT Compiler
│
└── Frameworks
     │
     ├── ASP.NET Core
     ├── Entity Framework Core
     ├── MAUI
     ├── Blazor
     └── gRPC
```

The .NET platform provides the runtime and core libraries.

ASP.NET Core is one of the frameworks built on top of .NET for creating web applications.

# Why Do We Use ASP.NET Core?

Our project exposes banking services through HTTP APIs.

ASP.NET Core provides everything required to build those APIs, including:

* HTTP server hosting
* Routing
* Controllers
* Model binding
* Dependency Injection
* Middleware
* Authentication
* Authorization
* Configuration
* Logging
* OpenAPI / Swagger support

Instead of building these features ourselves, ASP.NET Core provides them as part of the framework.

# The Architecture of an ASP.NET Core Application

At a high level, every ASP.NET Core application follows the same flow:

```text
Client

↓

HTTP Request

↓

Kestrel Web Server

↓

Middleware Pipeline

↓

Routing

↓

Controller

↓

Application Service

↓

Business Logic

↓

HTTP Response

↓

```

Our Bank Integration Platform follows this exact architecture.

# Kestrel

## What is Kestrel?

Kestrel is the web server built into ASP.NET Core.

Its responsibility is to:

* Listen for incoming HTTP requests.
* Parse HTTP messages.
* Create an `HttpContext`.
* Send HTTP responses.

Without Kestrel, our API would never receive requests.

---

## What Does Kestrel Actually Do?

When the application starts:

```text
Program.cs

↓

app.Run()

↓

Kestrel starts

↓

Port 5153 begins listening
```

When Swagger sends a request:

```text
POST /api/v1/balance
```

Kestrel receives that request before any of our code executes.

Only after Kestrel has created the request context does ASP.NET Core begin executing middleware.

---

# HttpContext

One of the most important objects in ASP.NET Core is `HttpContext`.

Every HTTP request gets its own instance.

It contains everything related to the current request, including:

* Request headers
* Request body
* Response headers
* Response body
* User information
* Cookies
* Query parameters
* Route values
* Items collection

Throughout this project we use `HttpContext.Items` to store the Correlation ID generated by our middleware.

---

# Program.cs

`Program.cs` is the application's entry point.

When the application starts, this file is executed first.

Its responsibilities include:

* Building the application.
* Registering services.
* Registering middleware.
* Configuring Swagger.
* Mapping controllers.
* Starting Kestrel.

Notice that `Program.cs` does **not** contain business logic.

Instead, it composes the application by connecting all of its components together.

---

# Dependency Injection Container

One of the first things we configure in `Program.cs` is the Dependency Injection (DI) container.

Example:

```csharp
builder.Services.AddScoped<IBankService, BankService>();
```

This tells ASP.NET Core:

> "Whenever a class asks for an `IBankService`, create and inject a `BankService`."

The framework automatically creates and manages object lifetimes for us.

A later chapter explains Dependency Injection in depth.

---

# Controllers

Controllers expose public HTTP endpoints.

For example:

```text
POST /api/v1/balance
```

The controller receives the request, calls the application service, and returns a response.

Controllers should remain lightweight.

Business logic belongs in the Application layer, not inside controllers.

---

# Middleware

Middleware is one of the defining features of ASP.NET Core.

Every incoming request passes through a pipeline of middleware components before reaching a controller.

Likewise, every response passes back through the same pipeline before being sent to the client.

In our project we currently have:

* CorrelationMiddleware
* ExceptionMiddleware

Later we will introduce:

* Logging middleware
* Authentication middleware
* Authorization middleware
* Performance monitoring

---

# Routing

Routing determines which controller and action should handle a request.

Example:

```text
POST /api/v1/balance
```

is routed to:

```text
BalanceController

↓

GetBalance()
```

Without routing, ASP.NET Core would not know which code should execute.

---

# Model Binding

Model Binding converts incoming HTTP data into C# objects.

When the client sends:

```json
{
  "accountNumber": "123456789",
  "bankCode": "SNB"
}
```

ASP.NET Core automatically creates:

```csharp
BalanceRequest request
```

No manual JSON parsing is required.

This automatic conversion greatly simplifies controller code.

---

# Swagger (OpenAPI)

Swagger provides interactive API documentation.

Instead of writing HTTP requests manually, Swagger allows developers to:

* Discover endpoints.
* View request models.
* View response models.
* Execute requests directly from the browser.
* Test APIs during development.

Swagger is intended for development and testing rather than production use.

# Why We Built the Project in This Order

The project was intentionally developed in incremental stages:

3. Added controllers.
4. Introduced services.
5. Introduced Dependency Injection.

Each step introduced a new concept while building upon the previous one.

This progression mirrors how many enterprise applications evolve over time.

# Common Misconceptions

### "ASP.NET Core is the web server."

Incorrect.

Kestrel is the web server.

ASP.NET Core is the framework running on top of .NET.

---

### "Controllers process requests directly."

Not exactly.

Requests always pass through the middleware pipeline before reaching a controller.

---

### "Program.cs contains application logic."

Incorrect.

`Program.cs` is responsible for configuring and composing the application, not implementing business behaviour.

---

### "Dependency Injection creates global objects."

Incorrect.

The DI container creates objects according to the lifetime that has been registered (Singleton, Scoped, or Transient).

---

# Best Practices

* Keep `Program.cs` focused on configuration.
* Keep controllers thin.
* Place business logic inside services.
* Register services using interfaces.
* Prefer middleware for cross-cutting concerns.
* Avoid hardcoding configuration values.
* Keep application layers loosely coupled.

# Key Takeaways

* ASP.NET Core is a modern framework for building web applications and APIs on the .NET platform.
* Kestrel is the web server that receives incoming HTTP requests.
* Every request has its own `HttpContext`.
* `Program.cs` configures and composes the application.
* Middleware executes before and after controllers.
* Routing selects the appropriate controller.
* Model binding converts HTTP data into C# objects.
* Controllers delegate work to services rather than containing business logic.
* Understanding the request pipeline is fundamental to understanding the rest of this project.
